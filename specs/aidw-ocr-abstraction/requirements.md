## 用語定義

| 用語 | 定義 |
|------|------|
| 重点5項目 | `focusFields = [customer, deliveryLocation, product, quantity, price]` の5キー。確認画面で常時表示する対象集合 |
| 第三象限 | 頻度×複雑性マトリクス上の「高頻度×低複雑性」領域（詳細は「第三象限の定義（暫定）節」） |
| プロファイル | クライアント固有のマスタ構造・OCR出力形・レビュールール・lookup 実装を束ねる `ClientProfile` インスタンス |
| 一意確定 | マスタ lookup 結果の `kind === 'unique'`。自動除外の発火条件 |

## 目的（Purpose — ユーザー視点）

OCR確認業務担当者が、**マスタ照合で一意決定可能な項目に時間を奪われず、人間判断が必要な項目だけに集中して確認を完了できる**状態を作る。

- 主要指標（定性）: 確認項目数の削減体感・重点項目への集中度
- 最上位の優先目的: 第三象限（高頻度×低複雑性）の自動化余地を、**クライアントごとに構造が異なる現実**を吸収しつつ UI として成立させる
- 目的は「OCR精度を上げる」ではなく「**確認レビュー体験を最適化する**」

### 第三象限の定義（暫定）

座標原点基準: **横軸=複雑性（左=低・右=高）、縦軸=頻度（下=高・上=低）**。したがって「第三象限」は左下＝**高頻度かつ低複雑性**の領域を指す。

| 軸 | 定義（暫定） |
|----|------------|
| 縦軸: 頻度 | 月あたり出現件数が多い（下方向=高頻度） |
| 横軸: 複雑性 | マスタ照合で一意決定可能な項目比率が高い（左方向=低複雑性） |

**操作的定義**: あるケースの OCR 後項目のうち、マスタ lookup で **unique hit** する項目が閾値以上のとき、そのケースを第三象限とみなす。閾値は金曜ヒアリング持ち越し（「暫定値と金曜ヒアリング持ち越し論点 #1」）。

## 機能要件（MoSCoW）

### Must（MVP必須）

| ID | 要件 | 受入基準（Yes/No） |
|----|------|-------------------|
| FR-M-1 | ClientProfile 抽象（masterSchema / ocrSchema / reviewRules）で2種以上のプロファイルを定義できる | プロファイル2種が同一UIコードから切替え可能か |
| FR-M-2 | OCR後データをプロファイル固有スキーマで受取り、共通エンベロープ（meta + items[]）に正規化する | プロファイルA/B双方でエンベロープ形状が同一か |
| FR-M-3 | マスタ lookup 共通IF（customer / deliveryLocation / product / price）を提供し、各プロファイルが実装を差し替えられる。**Must 範囲で A/B 両プロファイルを検証できる切替機構を提供**する。具体: URLクエリ `?profile={clientId}` または環境変数で Must 切替可能（UI セレクタの見た目整備は Should / FR-S-1） | 同一UIコードからプロファイル固有lookupが呼ばれるか・URLクエリで A/B を切替えて両者を検証できるか |
| FR-M-4 | 自動除外ロジック: OCR項目→lookup→一意確定の場合は確認フローから除外する | 一意確定項目が確認UIに出ないか |
| FR-M-5 | 重点5項目（`focusFields` = 取引先/納品先/商品/個数/価格）を確認画面に常時表示する | 5項目のセクションが視認できるか（一意確定分はトレース扱い） |

### Should

| ID | 要件 | 受入基準（Yes/No） |
|----|------|-------------------|
| FR-S-1 | プロファイル切替UI（画面上部のセレクタ等）でA/B を切替えて動作確認できる（Must の URLクエリ切替を UI に昇格） | 切替後に一覧・詳細双方が新プロファイルのデータで再描画されるか |
| FR-S-2 | 除外トレース表示: 自動除外された項目を折りたたみ等で確認可能にする | 除外項目の lookup 根拠（照合キー・ヒット値）が見えるか |

### Could（本プロトタイプでは未対応、明記のみ）

| ID | 要件 |
|----|------|
| FR-C-1 | 信頼度スコア表示（現在は二値: 確定 or 要確認） |

### Won't（今回やらない・スコープ外）

| ID | 要件 | 理由 |
|----|------|------|
| FR-W-1 | 実OCRエンジン連携 / 実マスタDB接続 / 認証 / プロファイル動的ロード / バリデーションフレームワーク導入 | プロトタイプ規約（YAGNI）。ダミーデータとビルド時 import で十分 |

## 受入基準（統合）

- **AC-M-1**: プロファイルA/B それぞれでダミーデータ**ちょうど10件**（うち unique 種別・multi 種別・none 種別を**各1件以上**含む）を一覧表示できる。URLクエリ `?profile={clientId}` で A/B を切替え、両プロファイルが同一UIコードで検証できる
- **AC-M-2**: 詳細画面で重点5項目が可視化され、一意確定項目は確認対象から外れている
- **AC-M-3**: OCR後データのロード時、`meta.requestId` 欠損または `items` 非配列のレコードは `console.warn` 出力し一覧から除外される（最小限の検証）
- **AC-M-4**: マスタ lookup 共通IF（customer / deliveryLocation / product / price）がプロファイル差替え可能な形で実装され、同一UIコードからプロファイル固有 lookup が呼ばれる
- **AC-M-5**: プロファイル追加時、`src/profiles/{clientId}/` 配下にファイル追加（`index.ts` + `masters.ts` + `ocr-samples.ts` 等必要ファイル）+ プロファイルレジストリ（`src/profiles/index.ts`）への1行追記のみで完結し、UI共通コード・`src/lib/ocr/*` に一切手を加えずに済む
- **AC-S-1**: プロファイル切替UI（セレクタ）で A→B に切替えると、一覧・詳細とも新プロファイルのスキーマ・マスタで再描画される（Should）
- **AC-S-2**: 除外トレースを展開すると、除外理由（lookup キー + ヒット値）が項目ごとに見える（Should）

## 非機能要件

**プロトタイプ規約により省略**。以下を明示的に非対象とする:

- パフォーマンス目標値
- 可用性・耐障害性
- セキュリティ要件（認証・認可・監査ログ）
- スケーラビリティ
- i18n / a11y の厳密対応
- ログ基盤・監視

手動動作確認（`pnpm dev` でプロファイルA/B切替・重点5項目表示・除外トレース確認）で十分とする。

## 暫定値と金曜ヒアリング持ち越し論点

本仕様は顧客（伊野さん）金曜ヒアリング前の**暫定値**で構成している。以下6点はヒアリング後に確定する。

| # | 論点 | 暫定値 | 確定すべき事項 |
|---|------|--------|--------------|
| 1 | 第三象限の定義軸・閾値 | 「高頻度×低複雑性」「unique hit 項目比率が閾値以上」 | 軸の採用可否・閾値の数値 |
| 2 | 重点5項目の妥当性 | 取引先 / 納品先 / 商品 / 個数 / 価格 | 過不足・業態別の差異 |
| 3 | 信頼度扱い | 二値（確定 or 要確認） | スコア表示の要否・閾値設計 |
| 4 | プロファイルA/B の業態差 | 未特定（ダミー2種） | 実在クライアント2社の業態・マスタ構造差 |
| 5 | 確定不能項目の扱い | 確認UIへ昇格 | エラー化 vs 昇格 vs 人手入力フォールバック |
| 6 | OCR誤読前提 | 誤読ありとして再確認可能にする | 再確認UIの粒度・修正手段 |

**運用ルール**: ヒアリング後、確定事項は requirements.md → design.md → tasks.md の順で反映する。未確定のまま実装着手する項目は Could / Won't に退避させる。

## 完了判定

Must と Should で完了境界を分離する。

- **Must完了（MVP成立）**: AC-M-1〜AC-M-5 **すべて Yes**。この時点で MVP は成立し、金曜ヒアリング前の暫定検証としてリリース可能
- **Should完了**: AC-S-1・AC-S-2 **すべて Yes**。Must完了後の上積みとして着手

Must完了のみで MVP は成立し、Should 未完了でもデモ用途として機能する。Should は Must 完了後の継続タスクとして扱う。

## スコープ境界

### やること（この仕様で定義する範囲）
- ClientProfile 抽象の定義
- プロファイル2種のダミー実装（各ちょうど10件・種別内訳: unique/multi/none 各1件以上）
- 画面遷移: プロファイル選択（or 切替UI）→ 一覧 → 確認詳細
- 重点5項目UI
- 自動除外ロジック
- 除外トレース表示（Should）

### やらないこと
- Won't 全項目（FR-W-1）
- 既存 aidw-ui-mock の機能改修（PDFプレビュー・価格差分閾値・編集バッファ等）
- プロトタイプの製品化を見据えた抽象化（DI / エラー体系 / Result<T>）
