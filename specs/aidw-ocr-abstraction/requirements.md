## 用語定義

| 用語 | 定義 |
|------|------|
| 重点5項目 | `focusFields = [customer, deliveryLocation, product, quantity, price]` の5キー。確認画面で常時表示する対象集合 |
| 象限3（=第三象限） | タスク×ドメインのマトリクス上、**汎用ドメイン×特定タスク**領域。1つのタスクを多業界で使い回す（詳細は「象限3の定義」節） |

## 目的（Purpose — ユーザー視点）

OCR確認業務担当者が、**マスタ照合で一意決定可能な項目に時間を奪われず、人間判断が必要な項目だけに集中して確認を完了できる**状態を作る。さらにこの体験を、特定の1業界・1顧客に閉じず**複数業界・複数顧客に展開可能**な形で実現する。

- 主要指標（定性）: 確認項目数の削減体感・重点項目への集中度・新規ドメイン追加コストの低さ
- 最上位の優先目的: 既存 `aidw-ui-mock`（象限1=特定ドメイン×特定タスク）を**象限3（汎用ドメイン×特定タスク）へ拡張**するための、クライアント別マスタ・OCR構造を吸収する抽象化層を UI として成立させる
- 目的は「OCR精度を上げる」ではなく「**確認レビュー体験を最適化し、それを多業界に展開可能にする**」

### 象限3の定義

タスク×ドメインのマトリクス上で本feature が狙う領域を定義する（社内議論資料準拠）。

座標基準: **横軸=タスク汎用度（左=特定タスク・右=汎用タスク）、縦軸=ドメイン汎用度（上=特定ドメイン・下=汎用ドメイン）**

| 象限 | 領域 | 例 |
|------|------|-----|
| 象限1（左上） | 特定ドメイン × 特定タスク | 個社の1業務×1タスクに集中（既存 `aidw-ui-mock` = 単一顧客のOCR確認） |
| 象限2（右上） | 特定ドメイン × 汎用タスク | 1業界に絞り複数タスクを横展開（例: 法務向けに要約・翻訳・分類） |
| **象限3（左下）** | **汎用ドメイン × 特定タスク**（**本feature**） | 1タスクを多業界で使い回す（例: OCR確認タスクを法務・物流・EC等に提供） |
| 象限4（右下） | 汎用ドメイン × 汎用タスク | あらゆる業界×あらゆるタスク（例: ChatGPT, Claude） |

**本feature のスコープ**: 既存 `aidw-ui-mock`（象限1）の OCR確認タスクを固定したまま、対応**ドメイン（顧客・業界・マスタ構造）**を切替可能化することで象限3に拡張する。OCR確認タスク自体の中身（マスタ照合による自動除外・重点5項目UI）は引き続き仕様の中核として維持。

## 機能要件（MoSCoW）

### Must（MVP必須）

| ID | 要件 | 受入基準（Yes/No） |
|----|------|-------------------|
| FR-M-1 | ClientProfile 抽象（masterSchema / ocrSchema / reviewRules）で2種以上のプロファイルを定義できる | プロファイル2種が同一UIコードから切替え可能か |
| FR-M-2 | OCR後データをプロファイル固有スキーマで受取り、共通エンベロープ（meta + items[]）に正規化する | プロファイルA/B双方でエンベロープ形状が同一か |

| FR-M-5 | 重点5項目（`focusFields` = 取引先/納品先/商品/個数/価格）を確認画面に常時表示する | 5項目のセクションが視認できるか（一意確定分はトレース扱い） |

## 受入基準（統合）

- **AC-M-1**: プロファイルA/B それぞれでダミーデータ**ちょうど10件**（うち unique 種別・multi 種別・none 種別を**各1件以上**含む）を一覧表示できる。URLクエリ `?profile={clientId}` で A/B を切替え、両プロファイルが同一UIコードで検証できる
- **AC-M-2**: 詳細画面で重点5項目が可視化され、一意確定項目は確認対象から外れている
- **AC-M-3**: OCR後データのロード時、`meta.requestId` 欠損または `items` 非配列のレコードは `console.warn` 出力し一覧から除外される（最小限の検証）
- **AC-M-4**: マスタ lookup 共通IF（customer / deliveryLocation / product / price）がプロファイル差替え可能な形で実装され、同一UIコードからプロファイル固有 lookup が呼ばれる
- **AC-M-5**: プロファイル追加時、`src/profiles/{clientId}/` 配下にファイル追加（`index.ts` + `masters.ts` + `ocr-samples.ts` 等必要ファイル）+ プロファイルレジストリ（`src/profiles/index.ts`）への1行追記のみで完結し、UI共通コード・`src/lib/ocr/*` に一切手を加えずに済む
- **AC-S-1**: プロファイル切替UI（セレクタ）で A→B に切替えると、一覧・詳細とも新プロファイルのスキーマ・マスタで再描画される（Should）
- **AC-S-2**: 除外トレースを展開すると、除外理由（lookup キー + ヒット値）が項目ごとに見える（Should）

## 金曜ヒアリング持ち越し5論点の仮決定値

本仕様は顧客（伊野さん）金曜ヒアリング前の暫定値で構成していた。5論点を analyst 側草案として**仮決定値**に置換する。金曜ヒアリング後、確定値との差分が出た場合は requirements.md → design.md → tasks.md の順で差替える（**差替可を明示**）。

| # | 論点 | 仮決定値 | 根拠 | 金曜確認事項 |
|---|------|----------|------|------------|
| 1 | 重点5項目 | **既存踏襲**: 取引先 / 納品先 / 商品 / 個数 / 価格 | 既存 aidw-ui-mock で実装済み・UX検証済み。業態差は#3で吸収するため本項目は不変 | 実在クライアント2社での過不足有無 |
| 2 | 信頼度扱い | **二値継続**: 確定 or 要確認 | プロトタイプ規約（YAGNI）。スコア閾値設計はヒアリング後に Could/Won't から昇格判断 | スコア表示要望の有無・閾値案 |
| 3 | A/B 業態差 | **ダミー継続**: client-a / client-b の2種は業態差を持たせないダミーで十分 | 実在クライアント特定前に擬似業態を作り込むと手戻りが大きい。抽象レイヤーの動作検証目的はダミーで達成可 | 実在2社の業態・マスタ構造差 |
| 4 | 確定不能項目（`none`/`multi`） | **確認UIへ昇格・編集可能化**: 表示のみではなく編集可能フィールドとして人手入力可 | /fax/* 統合に伴い既存編集UIを流用可能。表示のみ→編集可へ方針転換（従来MVP既定挙動から変更） | エラー化 vs 昇格の最終判断 |
| 5 | OCR誤読 | **編集可能UI昇格**: `unique` 判定項目も再確認・編集可 | /fax/* 統合により既存の編集UI資産を活用できるため、MVP段階でも再確認UIを提供可能 | 再確認UIの粒度・修正粒度 |

**方針転換の注記**: 従来 design.md §UI設計の `none`/`multi` MVP既定挙動「表示のみ・編集不可・承認不可」は、#4・#5 仮決定値により**編集可へ昇格**する。詳細は design.md 追補節「#4/#5 仮決定値に基づくUI挙動変更」を参照。（適用範囲: `/fax/[requestId]` のみ。`/ocr-abstraction/[requestId]` は既存MVP挙動維持）

**運用ルール**: 金曜ヒアリング後、確定事項との差分は requirements.md → design.md → tasks.md の順で反映する。未確定のまま実装着手しない項目は Could / Won't に退避させる。

### 追加受入基準

- **AC-M-6**: 設定画面 `/ocr-abstraction/settings` が存在し、マスタ構造は4ブロック（customer / deliveryLocation / product / price）それぞれで (a)キー一覧表 + (b)代表値1件JSON が同時表示される。OCR後データ構造は rawShape と OcrEnvelope の対比表示
- **AC-M-7**: 設定画面でプロファイルを A→B に切替えると、可視化表示が即時更新される
- **AC-M-8**: 設定画面または `/ocr-abstraction` のセレクタで A→B に切替えると、`/fax`（一覧）・`/fax/[requestId]`（詳細）の表示データも新プロファイルに従って切替わる

- **AC-S-3**: `/fax/[requestId]` で `none`/`multi` 項目が編集可能フィールドとして描画される（仮決定値 #4）
- **AC-S-4**: `/fax/[requestId]` で `unique` 項目も再確認・編集可能（仮決定値 #5）

### スコープ拡張に伴う境界変更

- 従来「aidw-ui-mock とは独立・`/fax/*` 分離運用」の分離境界を**解除**する（本spec自主設定の分離方針であり、CLAUDE.md §3 由来の不可侵領域ではない）
- 触ってよい範囲: `src/app/fax/*`・`src/types/request.ts` 等。store は並行 subscribe 方式（`src/store/store.ts` 改修なし、`ocr-store` を `/fax/*` から import し、**既存 store と並行 subscribe**）
- 触ってはいけない範囲（CLAUDE.md §3 準拠、不変）: テストファイル全般・`samples/` 配下・`public/samples/`・`public/pdfjs/`・`node_modules/`
- 詳細は design.md「分離境界の解除宣言」節を参照

### 採用アプローチの検討

採用: 候補A（`/fax/*` と `/ocr-abstraction/*` 併存、store は ocr-store 共有参照）。理由: YAGNI — 検証資産残存+最小侵襲。

## 完了判定

Must と Should で完了境界を分離する。

- **Must完了（MVP成立）**: AC-M-1〜AC-M-5 **すべて Yes**。この時点で MVP は成立し、金曜ヒアリング前の暫定検証としてリリース可能
- **Should完了**: AC-S-1・AC-S-2 **すべて Yes**。Must完了後の上積みとして着手

Must完了のみで MVP は成立し、Should 未完了でもデモ用途として機能する。Should は Must 完了後の継続タスクとして扱う。
